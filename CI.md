# CI request and result contract

AIConversationCore uses the pinned RepoWorkflow engine as its authoritative generic CI lifecycle. Expensive development validation is explicit-request gated, while stable `main` validation uses RepoWorkflow stable mode.

## Development cycle

1. Work on an issue branch using `x.y.z-issue.<issue>.<iteration>`.
2. Establish the issue-qualified version before substantive changes.
3. Run focused checks while developing.
4. When the candidate is ready, set `.ci/run-ci-request` to the exact authoritative development version and push the candidate.
5. The canonical RepoWorkflow adapter verifies repository/branch policy, materializes declared committed artifacts, validates the exact prepared commit, aggregates structured results, and publishes one immutable terminal result tag.

Authoritative version source: `package.json`, exposed to RepoWorkflow by `scripts/workflow-version.py`.

## Repository-owned validation

Core-specific validation remains in `scripts/repoworkflow-validate.py`. The required environment is declared in `.ci/repoworkflow.json` as `ubuntu-node22-python313` with Node 22 and Python 3.13. The hook preserves maintained file-size checks, production JSDoc coverage, the complete Node test suite, Phase 2 integrity, ChatGPT/Claude/Codex canonical goldens, provider-example regressions, and diff hygiene.

The deterministic browser bundle is a committed artifact declared in `.ci/repoworkflow.json`. `scripts/repoworkflow-build-browser.py` installs the locked Node dependency set and builds the bundle; `tests/browser-bundle.test.js` independently verifies the generated bytes before RepoWorkflow may commit them.

## Result semantics

RepoWorkflow owns PASS / FAIL / INCOMPLETE aggregation, exact-candidate cleanliness, immutable terminal result tags, and stable release tags.

- **PASS**: every required result is present and every required gate passed. Development mode publishes `v<issue-version>`.
- **FAIL**: every required result is present and at least one genuine required gate failed. Development mode publishes `v<issue-version>-CI-FAIL`.
- **INCOMPLETE**: a required result or prerequisite is unavailable; no terminal result tag is published.

Once a development iteration has a PASS or CI-FAIL terminal tag, source changes require the next issue iteration. Infrastructure failures that do not publish a terminal result tag may be corrected or retried on the same iteration.

## Stable release

A stable release candidate uses plain semantic versioning on `main`. RepoWorkflow stable mode verifies that exact authoritative `main` candidate, materializes and validates the deterministic browser bundle on the exact prepared commit, and publishes `vX.Y.Z` only after all required results pass.

## Workflow and policy ownership

`.github/workflows/ci.yml` must be byte-for-byte identical to the adapter in the pinned `RepoWorkflow/templates/github/ci.yml`. No second workflow may independently publish artifacts, mutate the branch, or publish result tags.

Core owns its repository data and validation semantics, including `.ci/branch-policy.json`, `.ci/repoworkflow.json`, `.ci/github.json`, the version/validation/artifact hooks, and Core-specific regression/golden tests. RepoWorkflow owns the generic orchestration, branch-policy engine, workflow-set policy, artifact commit boundary, result aggregation, and terminal-tag publication.
